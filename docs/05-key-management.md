# 05 — Key Management (cosign)

## Model: key-based cosign

Keyless (Fulcio/Rekor + OIDC) requires public OIDC and external egress, which does not fit a homelab.
We use **key-based** signing and always sign/attest **by digest**, never by tag.

## Key material

| Item | Location now | Target location |
|---|---|---|
| `cosign.key` (private, ECDSA P-256) | `security/cosign.key` on the agent (`chmod 600`) + k8s secret `boutique-ci/cosign-key` | **Vault** KV `boutique/ci/cosign` (Phase 6) |
| cosign password | `/tmp/opencode/cosign.password` (agent) + same k8s secret | Vault (Phase 6) |
| `cosign.pub` (public) | committed at `security/cosign.pub` | also consumed by Kyverno (Phase 8) |

The private key is **gitignored** and never committed. The public key is safe to publish.

## Operations

- **Sign by digest:** `cosign sign --key cosign.key <repo>@sha256:...`
- **Attest:** `cosign attest --type cyclonedx` (SBOM) and `--type slsaprovenance` (provenance).
- **Verify:** `cosign verify --key cosign.pub` and `cosign verify-attestation --type cyclonedx`.
- In CI, transparency-log upload is disabled (`--tlog-upload=false`) because the homelab cannot rely on
  the public Rekor log; verification therefore uses the key only. This is a **homelab trade-off**, recorded
  honestly — it means there is no independent transparency proof for these signatures.

## Provenance accuracy

The provenance attestation is a **SLSA-style predicate** generated by our own pipeline
(`builder.id = jenkins://boutique-app-ci`, source repo + commit SHA, build invocation id). It is
**SLSA Build L2-equivalent, not certified**. We do not overclaim.

## Rotation

1. Generate a new keypair (`cosign generate-key-pair`).
2. Store the new private key + password in Vault (`boutique/ci/cosign`), update the Jenkins/K8s secret.
3. Publish the new public key in `security/cosign.pub` and update the Kyverno policy (Phase 8).
4. Re-sign the currently deployed digests (or let the next build re-sign).
5. Keep the old public key with a `revoked-at` note for historical verification.

## Revocation / compromise

If `cosign.key` is exposed:
1. Immediately replace the key in Vault and the cluster secret.
2. Publish the new public key; update Kyverno to trust only the new key.
3. Re-sign all running digests; re-deploy via GitOps.
4. Audit all images signed with the compromised key and treat them as untrusted.
